# Custom tools (custom\)

> User-defined tool directory — when AI operations on some platform repeatedly fail, or when check / self-healing / report tools are needed, the AI reads the specs in this directory and generates custom tools (scripts / documents / other) for the project's actual situation.
> Entry order: this README → SCRIPT_SPEC.md (master spec: capability boundaries / generation flow / interface contract / platform adaptation) → SPEC_protocol_audit.md or SPEC_recovery.md (sub-specs).

## Purpose

Covers problems a pure-document protocol cannot check:
- Going through the motions (ticking the end-of-work check but not actually doing it) → end-of-work gate (SPEC_protocol_audit Checkpoint 1)
- Careless moves (changing files that should not be changed) → out-of-bounds changes (Checkpoint 2)
- Duplicate work (the same reports entry read twice) → distill-back-to-card validation (folded into the "Distilled" field validation of Checkpoint 1)
- Work conflicts (two AIs writing the same file at once) → concurrent conflict (Checkpoint 3)
- File corruption/loss → self-healing aids (SPEC_recovery)

## Files (this directory is the "local script generation spec")

| File | Description | When to read |
|---|---|---|
| `SCRIPT_SPEC.md` | Master spec: capability map / three-layer audit strategy / generation flow / unified interface contract / platform adaptation table | Required reading the first time you generate a script |
| `SPEC_protocol_audit.md` | Protocol-audit sub-spec: end-of-work gate / out-of-bounds / concurrency / ID and INDEX / naming and references / version drift / registry reconciliation | When generating "check-type" scripts |
| `SPEC_recovery.md` | Self-healing aids sub-spec: card rebuild / STATE recovery / anchor repair / stale version / archive consistency | When generating "recovery-type" scripts |

## What to generate & where to put it

| Artifact | Where it goes | In the skill package? |
|---|---|---|
| Script (e.g. check_local.ps1 / check_local.sh / check_local.py) | Project workspace root | ❌ No |
| Document (e.g. an extra spec) | Under tools\ in the project workspace | ❌ No |
| Other tools | Project workspace root | ❌ No |

**Principle**: custom tools generated by the AI do not enter the skill package — they live only in the project workspace and travel with the project.

## How to use

1. The user says "set up a local check script" / "AI operations keep failing" / "I need check or recovery tools"
2. The AI reads SCRIPT_SPEC.md (master spec) → asks the user three things (platform / which feature scripts to generate (default one feature per script) / where results land, and whether whole-set·group execution is needed) → reads the matching sub-spec
3. Generate single-platform, single-feature scripts (one feature per script) → put them in the project workspace root → self-check → state how to trigger them; when whole-category/cross-category batch execution is needed, provide the runner/groups per SCRIPT_SPEC "generation granularity and execution framework"
4. The pure-document protocol (the checks checklist) holds the "file shape" floor; the specs in this directory generate scripts that backstop "AI behavior / data corruption" problems

## Boundaries

- The specs give only "checkpoint logic + interface contract", never concrete implementation code — the AI generates per the platform adaptation table
- Scripts are single-platform implementations (PowerShell / bash / python3); no forced cross-platform cramming
- Scripts do not enter the skill package — they live only in the project workspace and travel with the project
- Semantic judgement (whether Key points are covered, whether content is true) → always mark [to be verified] and hand to the model/person; scripts do not hard-judge
- No proactive prompting: when the AI takes over work / creates a project it does not interrupt or ask "do you want to install scripts"; script generation is triggered by the manager (who decides after browsing to this directory), preserving work continuity

## Execution framework (script layer separated from execution layer)

- Scripts default to **one feature per script** (one independent script per Checkpoint/Recovery point); no big aggregate script;
- When batch execution is needed, use the "runner" to orchestrate: by default it groups whole sets automatically by filename prefix (check_* / recover_*), and it supports run_groups.json for customizing a higher-level cross-set grouping;
- For the detailed conventions see SCRIPT_SPEC.md "generation granularity and execution framework".
