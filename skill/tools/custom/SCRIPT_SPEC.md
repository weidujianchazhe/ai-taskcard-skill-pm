# 本地脚本规格总纲（SCRIPT_SPEC）

> **用途**：项目落地时，AI 通读本文件，按需读子规格（SPEC_protocol_audit / SPEC_recovery），向用户确认平台与模块后，生成单平台本地脚本放入项目工作区根目录。
> **触发**：用户说「建立本地检查脚本」「AI 操作老出问题」「我需要检查/自愈工具」时，AI 读本文件执行生成流程。
> **与技能的关系**：本文件是技能资产层规范（跨平台通用，纯 MD）；生成的脚本是项目工作区本地资产（单平台实现、不进技能包、随项目走）。
> **入口顺序**：custom\README.md（入口）→ 本文件（总纲）→ SPEC_protocol_audit.md / SPEC_recovery.md（子规格）。

## 一、能力地图：脚本能带来什么、不能做什么

### 能可靠做的（文件系统/格式层 —— 结论确定，可自动判定）

| 能力 | 抓什么 | 依赖的协议锚点 |
|---|---|---|
| 收工门禁 | 四件套核对打勾走过场、缺件漏件 | 最后折叠 / 上次交接 / 编号 |
| 漂移检测 | 三处同步副本版本不一致 | 版本行（v1.0.0） |
| 编号审计 | 分支未登记、跳号、撞号、非法类型 | 分支编号登记 / XXNNNN |
| 命名审计 | reports 命名违规、同名 | YYYY-MM-DD_主题_AI标识 |
| 引用审计 | 锚点悬空、INDEX 指向不存在 | 工程锚点 / 锚点组 |
| 越界改动 | 改了「涉及」以外文件 | 工程锚点 / 涉及 |
| 并发冲突 | 写前写后被他人插写 | mtime / 内容哈希 |
| 恢复脚手架 | 数据丢失后的重建草稿 | INDEX / reports（追加式） |
| 归档一致性 | reports 超阈值、done 对账 | archives 约定 |

### 不能做的（语义层 —— 结论不确定，禁止硬判）

| 能力 | 为什么脚本不能 | 处置 |
|---|---|---|
| 要点是否真的覆盖 reports 内容 | 语义比较 | 输出「待核」，交给模型/人 |
| 交接内容是否真实（做对而非写了） | 格式只能证「写了」 | 输出「待核」 |
| 废弃 / 接力 / 处置的价值判断 | 业务判断 | 交管理者 |

> **铁律 1**：脚本只输出三种结论——[通过] / [问题]（确定违规）/ [待核]（不确定，交给模型或人）。绝不把 [待核] 当 [问题] 或 [通过] 硬判。

### 三层审计策略（脚本不是唯一手段）

1. **脚本层**：本总纲各模块——抓格式/文件/完整性违规（廉价、可每天跑）。
2. **模型复核层**：把脚本输出的 [待核] 与可疑 [问题] 项，喂给当前 AI 用「审查提示词」复核语义（如：读锚点 reports，判断卡要点是否覆盖关键信息）——不另写脚本，用对话完成。
3. **人工终裁层**：复核仍存疑 → 列出给管理者决定（并写入 REVIEWS 阻碍点，事件自动采集）。

## 二、生成流程（AI 落地步骤）

1. 读本文件 → 读对应子规格 → 问用户三件事：
   ① 平台与运行环境：win + PowerShell？mac/linux + bash？是否有 python3？
   ② 要哪个模块：协议审计（SPEC_protocol_audit）还是恢复辅助（SPEC_recovery）还是全量？
   ③ 结果落哪：仅终端 / 写 reports\check_日期_主题_标识.md 并登记 INDEX / 两者
2. 生成单平台脚本 → 放入项目工作区根目录（如 check_local.ps1 / check_local.sh / check_local.py）。
3. 用样例路径自检一次 → 输出符合「统一接口契约」。
4. 告知触发方式：手动 / 收工后自动跑 / 计划任务（见 tools\schedule）。

## 三、统一接口契约（所有生成脚本必须遵守）

- **退出码**：0 = 全部通过；1 = 有 [问题]（确定违规）；2 = 有 [待核]；3 = 脚本自身错误
- **输出**：分段打印 [通过] / [问题] / [待核] + 「文件或行:具体描述」+ 问题附修复建议；不静默
- **默认只读**：除 SPEC_recovery 明确标注的写操作外，一律不改文件；修复类只输出建议，经用户确认后执行
- **平台自检**：脚本开头探测平台（win/mac/linux + 可用 shell），路径分隔符随平台；探测不到合法运行环境 → 退出码 3 并提示不适用
- **边界自觉**：任何「语义判断」一律归 [待核]，绝不伪装成 [问题]
- **资源节制**：脚本默认轻量——纯文本/文件检查，不引入重依赖；主机性能受限时用增量/抽样（只查最近 N 条、跳过全量 git diff），避免拖慢管理会话

## 六、持续运行与自动化边界

> 脚本能否「持续运行、彻底自动化对 AI 的管理与审核」？答案分层——确定性层可彻底无人值守，语义层永远不能。本节是生成常驻/定时脚本时必须遵守的边界。

### 能「彻底 + 持续 + 无人值守」的（确定性层）

| 持续任务 | 抓什么 | 对应缺陷 |
|---|---|---|
| 文件监听 watchdog | 并发写冲突、越界改动、改了文件却没走收工分流 | 纪律依赖 |
| 不变量校验 | 编号单调、命名规范、锚点完整、版本漂移、归档一致 | 格式层偷懒 |
| 收工门禁 | 声称收工 → 强制跑四件套验证，不通过不许走 | 打勾走过场 |
| 异常自动采集 | 恢复动作/违规 → 自动记 REVIEWS 阻碍点 | REVIEWS 只埋 3 处 |
| 维护提醒 | reports 超阈值、INDEX 满 N 行 → 自动提醒 | 归档遗漏 |

### 不能「彻底」自动化的（语义层 = 天花板）

| 永远审不了 | 为什么 |
|---|---|
| 代码/文档改动对不对（是否真解决了任务） | 正确性是开放问题 |
| 要点是否真的覆盖 reports 内容（沉淀是否真做） | 语义比较 |
| 交接写的「验证通过」是不是真验证了 | 格式只证「写了」，证不了「做了」 |
| 废弃/接力/处置的价值判断 | 业务判断 |

> 根本原因：脚本是确定性函数，语义是开放问题。任何「自动审语义」本质是再引入一个模型，而那个模型也会偷懒/出错——所以语义层永远是半自动，最后必须有人终裁。

### 持续运行的正确架构（三层，不是单一脚本死循环）

```
触发：定时（cron/计划任务） + 事件（收工后） + 手动
  ↓
脚本层（持续 · 只读 · 便宜 · 全自动）── 确定性检查，产出 [通过]/[问题]/[待核]
  ↓
模型复核层（定期批量 · 异常触发 · 有成本）── 只复核 [待核] 和可疑 [问题]
  ↓
人工终裁层（例外 · 低频）── 拍板废弃/处置，记 REVIEWS
```

**告警与节制原则**：
- 脚本不静默、也不刷屏——全通过时闭嘴，只报差异；
- [待核] 累积后批量喂给模型，不逐条打扰人；
- watchdog 增量/抽样，不全量扫描（呼应「资源节制」）。
- 待人工仲裁 = 异步排队、不阻塞工作：仲裁项只记录、不停机，人批量裁决后回溯应用；唯一阻塞点是「收工门禁」，且发生在收工边界（活已干完，卡在能否收工）、非工作中打断。审计是旁路，不是主链路。

### 落地时对生成脚本的硬约束

1. 常驻/定时脚本只做「确定性层」，遇到语义判断一律标 [待核]，禁止假装能审。
2. 「持续」依赖主机后台定时能力；无此能力的平台退化为「每次会话收工时自动跑一次」（伪持续，但仍有门禁价值）。
3. 全自动脚本的价值不是「彻底」，而是「把人的精力从盯格式解放到只审语义」。
