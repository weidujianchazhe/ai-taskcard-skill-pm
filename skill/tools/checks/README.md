# 检查协议（checks\）

> 本目录是检查协议说明文档（不是可执行脚本）——纯文档检查清单（人工/AI 对照打勾）。
>
> **触发方式**：人工触发=管理者明确要求时立即执行；收工门禁=每次声称完成前强制执行，失败阻塞完成；定期排查=仅 MAP 开关为「开」且到达计划周期时执行。三者不是同义触发。
> **可选时机（非强制）**：开工前 / 运行中 / 长期未动后——只是管理者可能检查的时机，不是必须检查。
> **开关**：可设置 AI 定期排查（开/关），**开关状态存于 MAP 规则段「AI 定期排查」**（改该行即切换），默认关闭；开启后才由 AI 定期执行。收工门禁不受此开关关闭影响。
> **AI 接手工作不做检查**：接手 AI 只读所需工作文件，不因检查而增加负担。

---

## 一、检查清单

> **类型选择**：用户说"检查工作记录/检查记录" → 用 checklist_record；用户说"检查整个项目/检查项目状态" → 用 checklist_project；用户没说 → 先问用户要哪种。

### checklist_record（工作记录检查）

- [ ] INDEX 类型标记正确（`[接力]`/`[完成]`/`[废弃]`），[接力] 链连续
- [ ] 任务卡覆盖式更新（无滚雪球、无历史堆积在卡内）
- [ ] STATE 覆盖式（人读区 + AI 区同步，时间戳最新）
- [ ] reports 命名规范（`YYYY-MM-DD_主题_AI标识.md`）
- [ ] 废弃需求已留痕（INDEX 一行 + 原因）
- [ ] 技能文件完整（对照 MAP 路径注册表清单；缺失项已从技能源包补全或标「待补」）

### checklist_project（项目排查）

- [ ] 任务卡均为活跃任务（完成即移卡到 archives\done\）
- [ ] 活跃卡卡尾含「收工协议速记」（协议钩子在位——缺速记的卡多为旧卡或重建漏抄，提示补上）
- [ ] 中断卡处理：承接非「—」但进度锚点停在半途且长期未动的卡 → 提示用户续作 / 改派 / 废弃（废弃由管理者决定，AI 只提示）
- [ ] 接手成本仍为「任务卡一张 ± 1 次 reports」（无膨胀点）
- [ ] 归档已执行（reports 篇数达到 MAP「reports 归档阈值」（默认 20）→ archives\；AI 收工时自动检查触发）
- [ ] 完成卡已移至 archives\done\（完成型收工不删卡，保留记录）
- [ ] 决策点已登记（STATE 决策点 / 任务卡要点）
- [ ] 存量项目：历史缺口标注「待按需整理」是否合理
- [ ] MAP 路径注册表与实际目录一致（无失效路径；对应审计检查点 7）—— v1.2.0
- [ ] reports\ 与 archives\ 无被删/被移文件（档案红线；被删时 INDEX 指针悬空 → 检查点 4 / 恢复点 3 可发现）—— v1.2.0
- [ ] TASK-ID / EVENT-ID / DESIGN-ID 稳定且引用可追溯
- [ ] INDEX_archived.md 不可变历史、主文件指针和归档 revision/hash 一致
- [ ] owner / revision / NORMALIZED-SHA256 / 原子写或 CAS 元数据齐全
- [ ] 当前模式的文件集、角色权限和升级条件满足

## 二、三态处置闭环

| 状态 | 处置 |
|---|---|
| 正常 | 记录「无问题」 |
| 需注意 | 记录问题 + 建议（不动文件） |
| 需处理 | 建任务卡 + 更新 STATE 决策点 + 写入 INDEX（[接力]） |

## 三、检查产出

- 检查结果写一条 reports 记录（`[完成]` 或 `[接力]` 类型），登记 INDEX
- 发现的问题转任务卡（按需处理），不直接大改文件
