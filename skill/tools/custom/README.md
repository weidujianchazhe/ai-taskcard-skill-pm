# 自定义工具（custom\）

> 用户自定义工具目录——当某平台 AI 操作反复出问题、或需要检查/自愈/报告工具时，AI 读本目录规范，根据项目实际情况生成自定义工具（脚本/文档/其他）。
> 入口顺序：本 README → SCRIPT_SPEC.md（总纲：能力边界/生成流程/接口契约/平台适配）→ SPEC_protocol_audit.md 或 SPEC_recovery.md（子规格）。

## 用途

覆盖纯文档协议检查不到的问题：
- 偷懒走过场（收工核对打勾但实际没做）→ 收工门禁（SPEC_protocol_audit 检查点 1）
- 蠢动作（改了不该改的文件）→ 越界改动（检查点 2）
- 重复动作（同一篇 reports 读了两次）→ 沉淀验证（并入检查点 1 的「最后折叠」校验）
- 工作冲突（两个 AI 同时写同一文件）→ 并发冲突（检查点 3）
- 文件损坏/丢失 → 自愈辅助（SPEC_recovery）

## 文件（本目录即「本地脚本生成规格」）

| 文件 | 说明 | 什么时候读 |
|---|---|---|
| `SCRIPT_SPEC.md` | 总纲：能力地图 / 三层审计策略 / 生成流程 / 统一接口契约 / 平台适配表 | 首次生成脚本必读 |
| `SPEC_protocol_audit.md` | 协议审计子规格：收工门禁 / 越界 / 并发 / 编号索引 / 命名引用 / 版本漂移 | 生成「检查类」脚本时 |
| `SPEC_recovery.md` | 自愈辅助子规格：卡重建 / STATE 恢复 / 锚点修复 / 版本过时 / 归档一致性 | 生成「恢复类」脚本时 |

## 生成什么 & 放哪里

| 产物 | 放哪里 | 是否进技能包 |
|---|---|---|
| 脚本（如 check_local.ps1 / check_local.sh / check_local.py） | 项目工作区根目录 | ❌ 不进 |
| 文档（如额外规范） | 项目工作区 tools\ 下 | ❌ 不进 |
| 其他工具 | 项目工作区根目录 | ❌ 不进 |

**原则**：AI 生成的自定义工具不进技能包——只在项目工作区里，随项目走。

## 使用方式

1. 用户说「建立本地检查脚本」/「AI 操作老出问题」/「我需要检查或恢复工具」
2. AI 读 SCRIPT_SPEC.md（总纲）→ 问用户三件事（平台 / 要生成哪些功能脚本（默认一功能一脚本）/ 结果落哪，及是否需要整集·分组运转）→ 读对应子规格
3. 生成单平台单功能脚本（一功能一脚本）→ 放项目工作区根目录 → 自检 → 告知触发方式；需要整类/跨类批量运转时按 SCRIPT_SPEC「生成粒度与运转框架」提供运转器/分组
4. 纯文档协议（checks 检查清单）守「文件形态」底线；本目录规格生成脚本兜底「AI 行为/数据损坏」问题

## 边界

- 规格只给「检查点逻辑 + 接口契约」，不给具体实现代码——AI 按平台适配表生成
- 脚本单平台实现（PowerShell / bash / python3），不跨平台硬凑
- 脚本不进技能包——只在项目工作区里，随项目走
- 语义判断（要点覆盖、内容真假）→ 一律标 [待核] 交模型/人，脚本不硬判
- 不主动提示：AI 接手工作/新建项目时不打断、不询问「是否要装脚本」；脚本生成由管理者主动触发（浏览到本目录后自行决定），保持工作连续性

## 运转框架（脚本层与运转层分离）

- 脚本默认**一功能一脚本**（每检查点/恢复点一个独立脚本），不生成聚合大脚本；
- 需要批量运转时用「运转器」编排：默认按前缀自动归类整集（check_* / recover_*），并支持 run_groups.json 自定义更高一级跨集分组；
- 详细约定见 SCRIPT_SPEC.md「生成粒度与运转框架」。
