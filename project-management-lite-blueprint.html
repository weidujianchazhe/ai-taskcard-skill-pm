Project Management Lite Work Assignment · Skill Design Blueprint

Generic "cross-barrier" project-management skill: multi-AI / cross-platform / cross-time / cross-project · task-card-driven (precise arrival, no guessing) · read on demand (however large the project, a task reads only what it needs) · human-read zone + AI zone (human-read summary + AI working coordinates)

Author: 如天之星 · License: MIT · Version v1.0.1 (in sync with the skill package)

Division of labor by module/branch · task-card-driven · overwrite-style update · human-read zone + AI zone

1. Positioning and Goals

Positioning: a generic project-management skill, not serving any specific project. Before any project starts, the AI reads this skill first, to initialize the collaborative workspace, follow the read/write handoff protocol, and continuously improve project management itself.

Essential goal (cross-barrier): cross the barriers of platform, AI, time and project, so that the AI taking over understands work requirements at a lower reading cost and makes fewer errors.

Core philosophy (read on demand): the project as a whole may be complex and heavy, but when the AI actually does the work it reads on demand only the part of the files relevant to the task —the burden does not grow with project size.

Mode of work (division by module/branch): trunk + branches + handoff within a branch — stable structure, feasible in parallel, continuous handoff.

Human-read zone + AI zone: every key file is divided into a "human-read summary zone" (the manager/executor/checker knows at a glance) + an "AI working-coordinate zone" (the taking-over AI works directly from it); the human-read zone is auto-generated from the AI zone and rewritten in sync, not aligned by subjective judgement.

Skill-size principle: add only what "existing mechanisms cannot cover"; anything platform-native, already covered by the existing protocol, or assumed to be needed only in the future is never implemented in the package (it may be registered as a protocol).

2. Target Structure (physical separation · naming is function)

The skill source package (external) and the project workspace layer (internal) are physically separated — **the management directory is created outside the code path** (not mixed into the source tree, not packaged); the project workspace is an instantiated copy of the skill (including protocol files); project source code is never written into the management directory.

Naming is function: MAP establishes structure → tasks\ locates → reports\ connects → STATE/INDEX on demand. Directory and fixed file names are in English (cross-platform compatible), content in Chinese; task cards are named after the work, in Chinese or English (defaults to the language the user communicates in).

3. Design Highlights (six modules + attached file)

Module 1 · Skill entry layer

  • SKILL.md: positioning statement, trigger timing (before a new project starts / before taking over a long-idle project / onboarding a legacy project), usage flow, management self-check list.
  • Initialization checklist: confirm the workspace root → create the management directory → replace MAP placeholders → register the first card → handoff template ready.

Module 2 · Parameter configuration layer

  • {WORKSPACE_ROOT}: confirmed once by the user at initialization (default or custom); the management directory's subfolders are created automatically by the skill.
  • {PLATFORM} (win/mac/linux), {SHELL} (powershell/bash).
  • The code path is provided by the user (code directory); the management directory is uniformly under {WORKSPACE_ROOT}\<project-name>\ (physically separated, not mixed into the source tree).
  • The MAP environment section's "[SKILL_SOURCE_PATH]" placeholder: registers the skill source package location at initialization (fill in "—" if not registered); version-drift detection and Recovery point 4 take it as input. The same section also has two placeholders: "[BACKUP_METHOD]" (git / periodic copy / none — disaster-recovery fallback registration for the source package) and "[DECISION_MAKER]" (the final decider for cross-branch conflicts, REVIEWS handling and meta-event escalation).
  • Dual-platform command examples + placeholder conventions: {} = runtime variables (evaluated by the AI / confirmed by the user), [] = project information (filled in by a human).

Module 3 · Collaboration protocol layer

  • Task-card-driven takeover: tasks\ is the first entry point (task card = Description + Key points + Code root path + Files involved + Last handoff + Distilled) → if sufficient, start work directly; if not, follow the anchor and read reports\ → if still unclear, ask the user.
  • MAP slimming mechanism: four fixed sections (environment/rules/protocol/path registry), written only when a path or structure is added, never records progress.
  • STATE boundary: mandatory reading for first takeover / cross-module / overall review; daily assigned tasks need not go through it (it assists review judgement).
  • End-of-work routing: unfinished → a card must be created (including work not yet carded, existing only in the current conversation); has a next step → full handoff (6 blocks + block 7) → overwrite-style update of the original task card; no next step → simplified summary + move the card to archives\done\ (do not delete the card, keep the completion record); after the four-piece set lands on disk, check item by item (handoff/card/INDEX/STATE — STATE is anentry-level write: read the latest before writing, update only your own task entry + the human-read zone, whole-file blind overwrite forbidden, so parallel end-of-work does not conflict).
  • Task-card overwrite-style update: update = overwrite fields (ID / Status / Description / Key points / Code root path / Files involved / Claimed by / Progress anchor / Last handoff / Distilled), no appending, no snowballing; the evolution trail belongs to reports\ + INDEX.
  • Task-card key-points field: 1-3 complete executable actions for the current task (what to do + which file, overwrite-style keeping the latest), serving the taking-over AI to work directly.
  • Task-card quality bar: Key points = executable actions (what to do + which file, no empty talk); Files involved = concrete file paths (no "related files"); Code root path = absolute path (cold start locates by it, no need to read MAP first); Last handoff = fill "—" only when there is no handoff; Distilled = the increments from reports already read have been written back into Key points.
  • Last handoff (chain entry, one or more allowed): one or more (trunk/each branch); when the full chain is needed, trace reports\ entry by entry along the anchor; no history is kept inside the card.
  • Distill back to card: after reading reports\, distill the increment back onto the card → each reports entry is read at most once → the takeover burden converges to "task card ± one reports entry".
  • Session = the scene, task card = persistence: writing the card at end of work is a mandatory distillation loop, preventing information from vanishing with the session; no double-write of session/card sync.
  • Task-card lifecycle: one read, one write (takeover reads but does not write; the card is written only at the two moments "new task" and "end-of-work update") + move the card to archives\done\ on completion.
  • Two sources of task cards: handoff-driven (auto-produced by block 7) + dispatch-driven (the manager copies the template to create a card after review).
  • Task card as the single form: all unfinished work is carded and written to disk (named after the work under tasks\), takeover reads a single card and the path is given directly; move the card to archives\done\ on completion.
  • INDEX type markers: [handoff]/[done]/[dropped] — takeover follows the [handoff] chain; done/dropped do not pollute the current judgement; dropped entries leave a trace (one line of topic + reason) to prevent mistaken work in future.
  • Lightweight bloat control: guard only the MAP slimming out-link + keep only active cards in tasks\; the rest is absorbed by read-on-demand.
  • Unified naming: MAP / STATE / tasks / reports / INDEX — the name is the function.
  • Concurrent-write rules: read-before-write (read the latest before overwrite-writing STATE/task cards or append-writing INDEX) · verify-after-write (read back after writing to confirm it landed) · STATE entry-level write (parallel end-of-work each updates its own entry, whole-file blind overwrite forbidden) · conflict adjudication (different fields merge; for the same field, within the same branch only, the larger ID number overwrites the smaller; cross-branch conflicts are not adjudicated by timestamp — cross-platform clocks are untrustworthy; both sides leave a trace in reports and hand it to the manager; increasing IDs + non-regressing timestamps are normal, reversed order makes the timestamp suspect) · collision retry (verify-after-write finds the same ID → the later writer rewrites this line with +1 and leaves a trace).
  • Gap filling: the skill source package is the authoritative source — if a project workspace skill file is missing or outdated (the source package version is higher) → copy the template from the source package and refill the instance (the source package path is registered in the MAP environment section "[SKILL_SOURCE_PATH]"); if a data file (task card/reports) is lost, recover it from INDEX/reports, and if INDEX is lost too → mark "data pending", do not fabricate; any recovery action also records one line of the obstacle in REVIEWS.md (meta-event collection, not into reports\).
  • Archive red line: deleting/moving any file under reports\ and archives\ is forbidden — the only exception = the end-of-work archiving flow (rolling archive past the threshold, moving completed cards); after moving, the corresponding INDEX row's pointer must be updated in sync; change records in three layers: MAP records structure (new paths/new branches, with Checkpoint 4 as the backstop for branch registration), reports records summaries (when the project has git, each "Changes" item carries a commit hash — a precise traceability anchor; when the full diff is needed, git show gives it), INDEX records pointer rows (double-write never loses).
  • Change-protection zone (SKILL.md Section 8): a hard gate for skill-package update/slimming/simplification/merging/field renaming — zero feature loss (only duplicate copies are reduced, never the single authoritative original) · cross-impact check (first check the references of checkpoints/recovery points/templates to the changed content; for a rename, first list the whole-package sync checklist; if a local simplification breaks the interplay with the check/recovery/handoff functions, do not do it at all) · takeover cost does not rise (files on the takeover path may only get thinner, never net-grow) · three cost-attribution principles (write path constant: end-of-work fields must be mechanically derivable, full-inventory-style fields forbidden; snapshot vs ledger division of labor: cumulative statistics belong to the INDEX archive and are queried on demand, cost may only move from high frequency → low frequency, never the reverse; main-file capacity is a hard cap: the INDEX main file's row count N is a reading-cost capping device, not expandable capacity — no adding rows on the grounds of being "more complete", and layered reads must not be merged) · load-bearing structures preserved (pointer chain / INDEX double-write / distill back to card / audit-dependency field list) · interlocking-chain warning (a protocol that looks like a few lines is often a multi-function junction node — before changing it, run the "six questions" self-check: who consumes it / is there an equivalent path / does the cost rise; prefer smaller over broken) · conflict means a popup (when the AI finds a change conflicting with the gate it must proactively alert the user and must not execute without confirmation, neither silently obeying nor silently letting it through) · reconciliation mindset (the document layer does no real-time supervision — supervision belongs to the script layer, and the document layer achieves "every action leaves a trace afterwards, multiple ledgers cross-verify, breaking the rules necessarily leaves a trace"; adjudication rules must not leave profit in forgery — the old "later timestamp wins" was a cheating-reward loophole and has been changed to corroboration only + manager adjudication; four reconciliation anchors of time/ID/identity/credential — the ID rule XXNNNN is the logical basis of Checkpoint 4 and the reconciliation interface, not a formatting preference, and any change must pass the cross-impact check).
  • reports date scheme YYYY-MM-DD_TOPIC_AI_TAG.md, AI tag {PLATFORM}-{AI_NAME}-{SHORT_CODE} (short code of 2-4 random characters, so multiple instances on the same platform do not collide).

Module 4 · Human-read zone + AI zone (human read + AI read)

  • One file, a unified human-read zone + AI zone pattern: human-read summary zone (3 fixed lines, serving the manager/executor/checker) + AI working-coordinate zone (serving the taking-over AI); the human-read zone is auto-generated from the AI zone (task ← first sentence of Description, status ← Status field, next step ← Key point 1, task distribution ← counts), rewritten in sync on overwrite updates, not aligned by subjective judgement (prevents forking).
  • Task-card human-read locator zone: project · module / task · stage / status · next step (3 fixed lines, overwrite style).
  • STATE top human-read zone: project positioning / task distribution / directory guide (3 lines, overwrite style).
  • The directory name is the category: current layer (STATE · tasks) / archive layer (reports) / index (INDEX); a human opening the directory knows which is which.
  • The INDEX table = the human-read index: date/type/topic/AI/handoff; a human sees the whole picture at a glance.

Module 5 · Optional tool zone (tools\, pulled on demand, not on the takeover path)

  • tools\README.md: registers built-in tools + anti-runaway rules (three iron rules: pull on demand / not on the takeover path / hold specifications only, not platform implementations).
  • checks\: the three moments (before work starts / during operation / after a long time) are optional moments — triggered on demand when the project manager needs them, not mandatory, not AI-automatic; the AI periodic-audit switch is off by default and can be turned on or off; the AI taking over work performs no checks and reads only the files it needs. checklist_record + checklist_project; a three-state handling loop. If a discipline problem recurs on a certain platform, a local check script can be added for that platform (single-platform implementation, not in the skill package).
  • visualize\: platform-independent specification; execution principles — analyze as far as possible · stop at the right point · resource restraint · complete information is the bottom line (no capability tiers; each AI analyzes to the maximum of its own ability while controlling token/compute usage).
  • schedule\: scheduled reminders / periodic checks / regular reporting; interlocked with the checks\ switch; implemented via each platform's scheduling capability.
  • report\: daily/weekly report data extraction (INDEX/STATE/reports), format, frequency.
  • custom\ (script generation spec): when an AI on a certain platform repeatedly has problems or deterministic auditing/self-healing is needed, the AI reads this directory's specs (SCRIPT_SPEC + SPEC_protocol_audit + SPEC_recovery) and generates a lightweight single-platform script according to the platform and host performance (not in the skill package). Boundary: the deterministic layer can run unattended continuously; the semantic layer marks [to be verified] → model re-check → human final ruling (asynchronous, non-blocking); generation is proactively triggered by the manager and can be called directly, and does not proactively prompt installation.
  • Protocol registration, not packaged implementation: search/translation/writing/minutes transcription/Q&A — registered in protocol form (when to use it, how the output is distilled); implemented via platform-native capabilities.

Module 6 · Meta-management loop (meta-management routing)

  • obstacle → root cause → suggestion → handling (manager) → landing (SKILL.md is the single source of truth, README/MAP are derived snapshots kept in sync) → use again; meta-events such as recovery/review/version drift are all registered in the workspace REVIEWS.md — they do not go into reports\, nor are they entered in INDEX; the project archive holds only project work records.
  • REVIEWS.template.md: the template lives in the skill source package and is instantiated at initialization as the workspace's REVIEWS.md (the sole landing point for meta-management events); four one-sentence sections (obstacle / root cause / improvement suggestion / handling decided by the manager); the manager manually extracts "recommend escalation" entries back into the skill source package; a deferred item is automatically reopened for review on its third recurrence.

Attached file · Legacy project onboarding (not in the main protocol)

  • LEGACY_ONBOARDING.md: guidance dedicated to projects already under way — creating the management directory is the universal first step (every project must create it; there is no start point where you read directly); a legacy project only additionally "lightweight-registers" the information visible in the current session and does no deep historical organization; history relies on the "progressive tidying mechanism" to classify as work proceeds and backfill on demand. At onboarding, copy the SKILL.md protocol entry (the MAP reference "collaboration protocol, see SKILL.md" points to it). After creation is done, the skill is not read again; work runs only on the working files.

Platform compatibility (prerequisite for use)

This skill is a local project-management engineering setup; prerequisites: a local file system + command/file execution capability (able to write the management directory to disk and read/write task cards and handoff files). Platforms are judged by capability dimension, not by enumerating platform names — any platform with the above capabilities (Harness-type / IDE Agent / desktop workspace Agent, etc.) is automatically compatible; it depends on no platform-private interface, skill system or API. Scenarios without local file capability (web chat / mobile App / pure conversation / raw API calls) do not meet the prerequisite and do not apply.

4. Reading Model (takeover reads one card · append on demand)

Taking-over AI:
1) Read the task card (Description + Key points + Files involved + Last handoff) → sufficient → start work directly (zero reads of reports)
2) Key points insufficient → follow the anchor and read the previous reports\ entry ([handoff] chain)
   → distill the increment back onto the card → the next takeover need not read this entry again
3) Need to trace further back / review → INDEX locates by [handoff] marker → read on demand
4) First takeover / cross-module / overall review → read STATE (including the human-read zone) and MAP

Decision mechanism (when reading history):
├─ [handoff] → a chain node, read it (current related work context)
├─ [done] → already done, do not read (read only for review/archiving)
└─ [dropped] → dropped requirement, do not read (a trace is left to prevent mistaken work)
Convergence effect: each reports entry is read at most once (distilled into the card); takeover cost ≈ one task card, occasionally ±1 reports entry; project scale does not enter the daily burden.
