项目管理轻量化工作分配 · 技能设计蓝图

通用型「跨阻碍」项目管理技能：多 AI / 跨平台 / 跨时间 / 跨项目 · 任务卡驱动（精准到达，不靠猜）· 按需读取（项目再大，任务只读所需）· 双阅读层（人读摘要 + AI 工作坐标）

作者：如天之星 · 许可证：MIT · 版本 v1.0.0

树链式 · 任务卡驱动 · 覆盖式更新 · 双阅读层

一、定位与目标

定位：一套通用型项目管理技能，不为特定项目服务。任何项目开工前，AI 先读取本技能，用于初始化协同工作区、遵守读写交接协议、持续优化项目管理本身。

本质目标（跨阻碍）：跨越平台、AI、时间、项目等阻碍，让接手的 AI 以更小读取代价理解工作需求、降低出错率。

核心哲学（按需读取）：项目整体可以复杂沉重，但 AI 实际落地工作时只按需读取与任务相关的一部分文件——负担不随项目规模增长。

工作形态（树链式）：主干 + 分支 + 分支内接力——结构稳定、并行可行、接力连续。

双阅读层：每个关键文件都分「人读摘要区」（管理者/执行人/检查人扫一眼即知）+「AI 工作坐标区」（接手 AI 直接干活）；人读区为 AI 区派生视图，机械重写，不靠主观对齐。

技能体量原则：只加"现有机制覆盖不了"的；平台原生就有、现有协议已覆盖、假设未来才需要的，一律不打包实现（可协议登记）。

二、目标结构（双层隔离 · 命名即职能）

技能资产层（外置）与项目工作区层（内置）物理隔离——**管理目录建在工程路径之外**（不混入源码树、不被打包）；项目工作区为技能实例化副本（含协议文件），工程源码永不写入管理目录。

命名即职能：MAP 认结构 → tasks\ 定位 → reports\ 衔接 → 按需 STATE/INDEX。目录/固定文件名英文（跨平台兼容），内容中文；任务卡按工作命名，中文/英文均可（默认随用户沟通语言）。

三、设计要点（六个模块 + 附带文件）

模块 1 · 技能入口层

  • SKILL.md：定位声明、触发时机（新项目开工前 / 长期未动项目接手前 / 存量项目接入）、使用流程、管理自检清单。
  • 初始化检查清单：工作区根确认 → 管理目录创建 → MAP 占位符替换 → 首卡登记 → 交接模板就绪。

模块 2 · 参数配置层

  • {WORKSPACE_ROOT}：用户初始化时确认一次（默认或自定义）；管理目录子文件夹由技能自动创建。
  • {PLATFORM}（win/mac/linux）、{SHELL}（powershell/bash）。
  • 工程路径由用户提供（代码目录）；管理目录统一在 {WORKSPACE_ROOT}\<项目名>\（物理隔离，不混入源码树）。
  • 双平台命令示例 + 占位符约定：{} = 运行期变量（AI 求值/用户确认），[] = 项目信息（人填）。

模块 3 · 协作协议层

  • 任务卡驱动接手：tasks\ 第一入口（任务卡 = 描述 + 要点 + 工程锚点 + 涉及 + 锚点组 + 最后折叠）→ 够用直接开工；不够沿锚点读 reports\ → 仍不明问用户。
  • MAP 精简机制：固定四段（环境/规则/协议/路径注册表），只在新增路径/结构时写入，永不记进展。
  • STATE 边界：首次接手/跨模块/整体审视必读，日常指定任务不必经（审视判断辅助）。
  • 收工分流：未完成 → 必须建卡（无论是否即时复制型）；有下一步 → 完整交接（6 块 + 第 7 块）→ 覆盖式更新原任务卡；无下一步 → 简化总结 + 移卡到 archives\done\（不删卡，保留完成记录）；四件套落盘后逐项核对（交接/卡/INDEX/STATE）。
  • 任务卡覆盖式更新：更新 = 覆盖字段（编号/状态/描述/要点/工程锚点/涉及/锚点组/最后折叠），不追加、不滚雪球；演进轨迹归 reports\ + INDEX。
  • 任务卡要点字段：1~3 条当前任务的完整可执行动作（做什么 + 在哪文件，覆盖式保留最新），服务接手 AI 直接干活。
  • 任务卡质量门槛：要点=可执行动作（做什么+在哪文件，禁止空话）；涉及=具体文件路径（禁止"相关文件"）；工程锚点=绝对路径（冷启动凭此定位，不必先读 MAP）；上次交接=无交接才填「—」；最后折叠=读过的 reports 增量已回填要点。
  • 上次交接 = 锚点组（链条入口）：一条或多条（主干/各分支），需要完整链条时沿锚点逐篇追溯 reports\，卡内不留历史。
  • 沉淀再前进：读 reports\ 后提炼增量覆盖回卡 → 每篇 reports 最多被读一次 → 接手负担收敛为"任务卡 ± 一次 reports"。
  • 会话 = 现场、任务卡 = 持久化：收工必写卡是强制提炼闭环，防信息随会话消失；不做会话/卡同步双写。
  • 任务卡生命周期：一读一写（接手读不写；写卡仅「新建任务」「收工更新」两时机）+ 完成即移卡到 archives\done\。
  • 任务卡两来源：交接驱动（第 7 块自动产出）+ 派单驱动（管理者审视后复制模板落卡）。
  • 任务卡单形态：所有未完成工作均建卡落盘（tasks\ 下按工作命名），接手读单卡，路径直接给到；完成即移卡到 archives\done\。
  • INDEX 类型标记：[接力]/[完成]/[废弃]——接手沿 [接力] 链走，完成/废弃不污染当前判断；废弃留痕（一行主题+原因）防未来误做。
  • 膨胀轻管控：只守 MAP 精简外链 + tasks\ 只留活跃；其余靠按需读取吸收。
  • 命名统一：MAP / STATE / tasks / reports / INDEX——名字即职能。
  • 内容级并发安全：写前读（覆盖写 STATE/任务卡、追加写 INDEX 前先读最新）· 写后验（写后读回确认落盘）· STATE 独占（当前负责 AI 更新，并行 AI 只写自己的卡与 reports）· 冲突裁决（不同字段合并、同字段仅在同分支内按编号数字大覆盖小；跨分支以时间戳后写为准并在 reports 留双方记录；编号递增 + 时间戳不倒退为正常，倒序则时间戳可疑）。
  • 缺失补全：技能资产层为权威源——项目工作区技能文件缺失或过时（资产层版本更高）→ 从资产层复制模板实例化重填（对照 MAP 路径注册表）；数据文件（任务卡/reports）丢失从 INDEX/reports 恢复，INDEX 也丢了 → 标「数据待补」，不伪造；任何恢复动作顺手记一行 REVIEWS 阻碍点（事件自动采集）。
  • reports 日期制 YYYY-MM-DD_主题_AI标识.md、AI 标识 {平台}-{AI名}。

模块 4 · 双阅读层（人读 + AI 读）

  • 同一文件、双阅读层统一模式：人读摘要区（3 行固定，服务管理者/执行人/检查人）+ AI 工作坐标区（服务接手 AI）；人读区为 AI 区派生视图（任务←描述首句、状态←状态字段、下一步←要点①、任务分布←计数），覆盖更新时机械重写，不靠主观对齐（防分叉）。
  • 任务卡人读定位区：项目·模块 / 任务·阶段 / 状态·下一步（3 行固定，覆盖式）。
  • STATE 顶部人读区：项目定位 / 任务分布 / 目录指引（3 行，覆盖式）。
  • 目录名即分类：当前层（STATE · tasks）/ 档案层（reports）/ 索引（INDEX），人打开目录即知哪类。
  • INDEX 表格 = 人读索引：日期/类型/主题/AI/交接，人扫一眼看全貌。

模块 5 · 可选工具区（tools\，按需拉动、不进接手路径）

  • tools\README.md：登记内置工具 + 防失控规则（三铁律：按需拉动 / 不进接手路径 / 只放规范不放平台实现）。
  • checks\：三个时机（开工前/运行中/长期后）是可选时机——项目管理者有需求时按需触发，非强制、非 AI 自动；AI 定期排查开关默认关闭，可开可关；AI 接手工作不做检查，只读所需文件。checklist_record + checklist_project；三态处置闭环。若某平台纪律问题反复出现，可针对该平台补本地检查脚本（单平台实现、不进技能包）。
  • visualize\：平台无关规范；执行原则——尽力分析 · 点到即止 · 资源节制 · 信息完整是底线（不设能力分级，按各 AI 自身能力最大化分析，同时控制 token/计算占用）。
  • schedule\：定时提醒/周期检查/定期汇报；与 checks\ 开关联动；实现靠各平台定时能力。
  • report\：日报/周报取数（INDEX/STATE/reports）、格式、频率。
  • custom\（脚本生成规格）：某平台 AI 反复出问题或需确定性审计/自愈时，AI 读本目录规格（SCRIPT_SPEC + SPEC_protocol_audit + SPEC_recovery），按平台与主机性能生成单平台轻量脚本（不进技能包）。边界：确定性层可持续无人值守；语义层标 [待核] → 模型复核 → 人工终裁（异步不阻塞）；生成由管理者主动触发、可直接调用，不主动提示安装。
  • 协议登记不打包实现：搜索/翻译/写作/纪要转写/问答——以协议形式登记（何时用、产出如何沉淀），实现靠平台原生能力。

模块 6 · 元管理回路

  • 阻碍 → 根因 → 建议 → 处置（管理者）→ 落地（同步 3 处 + 版本递增）→ 再使用；恢复动作发生时事件自动采集阻碍点。
  • REVIEWS.template.md：技能资产层（不进项目工作区、不进 tools\）——服务技能本身，四段一句话（阻碍点/根因/改进建议/处置由管理者决定）；暂缓项第 3 次复发自动翻案复审。

附带文件 · 存量项目接入（不进主协议）

  • LEGACY_ONBOARDING.md：已开工项目专用引导——创建管理目录是通用第一步（任何项目都要创建，不存在直接读取的起点）；存量项目只多「轻量登记」当前会话可见信息，不做深度历史整理；历史靠「渐进整理机制」边工作边归类、按需补录。接入时复制 SKILL.md 协议入口（MAP「协同协议详见 SKILL.md」引用指向它）。创建完成后不再重复读取技能，只按工作文件运行。

平台兼容（使用前提）

本技能为本地项目管理工程，使用前提：本地文件系统 + 命令/文件执行能力（能落盘管理目录、读写任务卡与交接文件）。平台按能力维度判定，不枚举平台名称——具备上述能力的平台（Harness 类 / IDE Agent / 桌面工作区 Agent 等）自动兼容；不依赖任何平台私有接口、技能系统或 API。无本地文件能力的场景（网页对话 / 移动端 App / 纯对话 / API 裸调）不满足前提，不适用。

四、读取模型（接手必读一张卡 · 按需追加）

接手 AI：
① 读任务卡（描述 + 要点 + 涉及 + 锚点）→ 够用 → 直接开工（reports 零读取）
② 要点不够 → 沿锚点读 reports\ 上一篇（[接力] 链）
   → 提炼增量覆盖回卡 → 下次接手不必再读这篇
③ 要追溯更早 / 审视 → INDEX 按 [接力] 标记定位 → 按需读
④ 首次接手 / 跨模块 / 整体审视 → 读 STATE（含人读区）与 MAP

判断机制（读历史时）：
├─ [接力] → 链条节点，读（当前相关工作上下文）
├─ [完成] → 已完成，不读（审视/归档才读）
└─ [废弃] → 废弃需求，不读（留痕防误做）
收敛效果：每篇 reports 最多被读一次（沉淀进卡）；接手成本 ≈ 任务卡一张，偶尔 ±1 次 reports；项目规模不进入日常负担。
